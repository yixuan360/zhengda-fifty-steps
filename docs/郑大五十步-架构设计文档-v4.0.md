## 三、数据架构设计

### 3.1 核心原则

**本地为主 + 简单在线同步。** 核心触发与播放链路 100% 离线可用，网络仅用于首次数据拉取和登录认证。

### 3.2 数据分层

| 数据类型 | 存储位置 | 更新机制 |
|----------|----------|----------|
| 景点信息（含图片/音频URL） | App 本地 SQLite | 启动时全量拉取（100 个景点以内，数据量极小） |
| 全局配置 | 本地默认 + 后端覆盖 | 启动时拉取，失败沿用本地默认值 |
| 音频文件 | 手机存储 | 首次播放时下载，后续复用本地文件 |
| 用户信息 | 后端 MySQL + 客户端缓存 | 登录时获取 |

### 3.3 同步机制（极简版）

**景点数据量极小（< 100 条），不做复杂的增量同步。**

```
App 启动（或下拉刷新）
  → GET /api/v1/spots/  拉取全部景点（含 imageUrl、audioUrl）
  → SQLite 单事务内：DELETE 旧数据 → INSERT 新数据（全量替换）
  → 同步失败 → 静默跳过，沿用本地数据
```

> **为什么不用增量同步？** V1 景点不超过 100 个，每条记录含文本不超过 10KB，全量拉取仅 ~1MB。同步耗时 < 1s，增量方案的开发和调试成本远超这 1s 的流量节省。等景点数量超过 500 个再考虑增量。

**并发保护**：同步入口加 `isSyncing` 标志位，重叠请求直接返回。

### 3.4 时间与坐标

- 服务端 UTC 存储，接口返回毫秒 Unix 时间戳（INTEGER），客户端 SQLite INTEGER 存储
- 坐标全链路统一 GCJ-02：服务端录入即 GCJ-02，客户端 GPS 定位由 LocationService 底层转 GCJ-02 后输出

## 六、核心业务设计

### 6.1 导览引擎（useTour Hook）

**全部逻辑集中在一个 `useTour.ts` 文件中**，不拆分为多个 service/manager。

```
useTour 内部逻辑：

1. 订阅位置变化（throttle 1次/s）
2. accuracy > 20m → 暂停触发，提示用户
3. accuracy ≤ 20m → Haversine 计算与所有 active 景点距离
4. 距离 ≤ triggerRadius（50m）→ 滞回检查防抖动 → 触发播放
5. 正在播放时新景点命中 → 弱提示"发现新景点"，用户确认后切换
6. 播放完成 → 该景点 60s 冷却 → 写入 play_history
7. 播放异常 → 自动重置，Toast "播放失败，请重试"
```

**滞回机制**：进入 ≤ 50m 触发，离开 > 70m 确认，20m 缓冲带防 GPS 抖动。

**多景点冲突**：同时命中按距离最近优先，其余加入内存队列顺位播放。

**冷却规则**：单景点独立冷却 60s，离开触发区域后自动重置。

### 6.2 核心链路

```
GPS 定位更新（WGS-84 → GCJ-02 转换）
  → 更新位置 state
  → useTour 节流判定（1次/s）
  → 精度检查 → Haversine 计算距离
  → 命中触发半径 + 滞回确认 → 调用 useAudioPlayer 播放
  → 播放完成 → 冷却 + 写入本地 play_history
  → UI 订阅 state 变化 → 弹出/收起播放卡片
```

## 七、API 接口规范

### 7.1 统一响应格式

```typescript
interface ApiResponse<T> {
  ok: boolean;         // true=成功, false=失败
  data: T;             // 业务数据
  message: string;     // 错误时返回提示信息
}
```

> **不使用自定义 5 位错误码**。HTTP 状态码（200/400/401/404/500）已经足够表达语义，附加一个 `message` 字段给前端展示即可。

## 八、数据库设计

### 8.1 服务端 MySQL

```sql
-- 用户表（扩展 AbstractUser）
-- Django 自动生成 auth_user + 额外字段：openid, unionid, nickname, avatar_url

-- 景点表（图片和音频 URL 直接在表中，不拆子表）
CREATE TABLE spots (
  id              INT AUTO_INCREMENT PRIMARY KEY,
  name            VARCHAR(100) NOT NULL,
  lat             DOUBLE NOT NULL,
  lng             DOUBLE NOT NULL,
  trigger_radius  INT DEFAULT 50,
  summary         TEXT,
  description     TEXT NOT NULL,
  image_url       VARCHAR(500),              -- 景点图片 URL（V1 一张图）
  audio_url       VARCHAR(500),              -- 音频 URL（V1 一个音频）
  is_active       TINYINT(1) DEFAULT 1,
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 全局配置
CREATE TABLE global_config (
  `key`         VARCHAR(100) PRIMARY KEY,
  `value`       JSON NOT NULL,
  updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> **为什么不用 SpotMedia 子表？** V1 每个景点只需一张图 + 一个音频，`image_url` / `audio_url` 直接放在 spots 表中查询更简单。多图/多语言是 V2 的事，届时加表即可。

### 8.2 客户端 SQLite

```sql
-- 景点表（全量同步自服务端）
CREATE TABLE spots (
  id              INTEGER PRIMARY KEY,
  name            TEXT NOT NULL,
  lat             REAL NOT NULL,
  lng             REAL NOT NULL,
  trigger_radius  INTEGER DEFAULT 50,
  summary         TEXT,
  description     TEXT NOT NULL,
  image_url       TEXT,
  audio_url       TEXT,
  is_active       INTEGER DEFAULT 1,
  updated_at      INTEGER                -- 毫秒 Unix 时间戳
);

-- 全局配置
CREATE TABLE global_config (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

-- 播放历史（仅本地存储，V1 不上报）
CREATE TABLE play_history (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  spot_id   INTEGER NOT NULL,
  played_at INTEGER NOT NULL,
  FOREIGN KEY (spot_id) REFERENCES spots(id) ON DELETE CASCADE
);
```

> **数据库升级策略**：V1 表结构稳定，不做 Migration 框架。App 启动时检测表是否存在 → 不存在则 `CREATE TABLE` → 已存在则直接使用。若 V2 需改表结构，App 启动时 `ALTER TABLE` 或删表重建（反正数据全量同步，无丢失风险）。

## 十、文件处理与缓存

### 10.1 图片与音频

- 管理员通过 Django Admin 上传 → 存入 `MEDIA_ROOT/`
- Nginx 直接代理 `/media/`，不经过 Django
- App 获取 URL → **按需下载**（首次播放/浏览时下载，后续走本地文件）
- 音频文件启用 `Accept-Ranges: bytes`，支持进度拖动

### 10.2 缓存策略（极简版）

**不做分池、不做 LRU。** 策略就一条：

- 设置总缓存目录上限 **500MB**
- 超出上限 → 清空整个缓存目录（图片 + 音频一起删）
- 内置 APK assets 中的兜底音频永远不被清除

> 校园场景典型用户安装后使用几次，缓存很难超过 500MB。等实际碰到超限问题再细化策略。

### 10.3 下载失败处理

- 下载失败 → 显示占位图 / Toast 提示
- 用户下次进入景点时文件不存在会重新触发下载（天然兜底）
- **不做重试队列、不做指数退避**

### 10.4 Nginx 配置

```
# 公开 API 限流（每 IP 每秒 10 次）
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

location /media/ {
    alias /var/www/zhengda/media/;
    expires 30d;
}

location /api/ {
    limit_req zone=api_limit burst=5 nodelay;
    proxy_pass http://127.0.0.1:8000;
}

location /admin/ {
    proxy_pass http://127.0.0.1:8000;
}
```

## 十五、架构决策记录（ADR）

| # | 决策项 | 选择 | 核心理由 |
|---|--------|------|----------|
| 1 | 开发框架 | React Native + Expo | 开发效率高，跨平台潜力保留 |
| 2 | 架构模式 | 页面 + Hook + Store（无多层嵌套） | V1 逻辑简单，扁平结构足够 |
| 3 | 地图方案 | 高德（react-native-maps + 瓦片） | 坐标系简单，RN 社区成熟 |
| 4 | 状态管理 | Zustand | 轻量、TS 友好 |
| 5 | 数据同步 | 全量拉取 | 景点 < 100 条，~1MB，增量方案过度设计 |
| 6 | 用户认证 | 微信登录 + JWT + 游客模式 | 校园场景门槛最低 |
| 7 | 管理后台 | Django Admin（V1） | V1 需求完全覆盖，砍掉独立前端 |
| 8 | 文件存储 | V1 本地磁盘 | 2 周工期先跑通 |
| 9 | 音频方案 | react-native-track-player | 后台播放 + 锁屏控制是刚需 |
| 10 | 仓库策略 | Monorepo | 单人开发减少上下文切换 |
| 11 | 测试策略 | pytest 关键逻辑 + 手动 checklist | V1 最务实的 ROI |
| 12 | 坐标系统一 | 全链路 GCJ-02 | LocationService 底层强制转换 |
| 13 | 软删除 | isActive 字段 | 取消 deletedIds，简化合并 |
| 14 | 数据库模型 | 单表（不拆 SpotMedia） | V1 一景点一图一音频，单表更简单 |
| 15 | 音频合成 | V1 同步阻塞 | 管理员低频操作，3-5s 可接受 |
| 16 | Django 架构 | View 直接处理逻辑 | V1 业务极简，Service 层是过度抽象 |
| 17 | 部署方式 | git pull + systemctl restart | 课程项目不需要 CI/CD |
| 18 | 缓存策略 | 目录总上限 500MB，超出清空 | LRU 分池是过度设计 |
| 19 | 客户端 DB 升级 | 检测表存在 → 不存在则建表 | V1 表结构稳定，不需要 Migration 框架 |
